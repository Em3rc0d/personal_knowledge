# MK0 Candidate Rules and Anti-patterns

These are **candidate operating rules**, not certified universal laws.

## R-001 — optimize for opportunities, not creator vanity

Primary business metric:

```text
Opportunities Generated
```

Track at minimum:

- recruiter DMs;
- interviews;
- referrals;
- client inquiries;
- proposals;
- contracts;
- collaborations;
- invitations;
- relevant portfolio visits;
- high-value new connections.

Likes are diagnostic, not the North Star.

## R-002 — use SQL as acquisition, not identity

Current evidence supports SQL as a **reach engine**.

Do:

- exploit counterintuitive SQL behavior;
- keep it accessible to students/juniors;
- use the distribution to expose deeper engineering content.

Do not:

- make every post SQL;
- allow the profile identity to collapse into “SQL account”;
- repeat recent SQL hooks/topics just because prior ones worked.

## R-003 — use the counterintuitive learning loop

High-performing reach content should prefer:

```text
known concept
  ↓
apparently obvious assumption
  ↓
counterintuitive behavior
  ↓
small reveal / explanation
  ↓
low-friction question
```

Psychological sequence:

```text
“I know this”
→ “wait…”
→ “ah”
→ save / react / answer
```

## R-004 — every content slot has a job

Portfolio-level mix:

- Reach Engine: ~25%
- Engineering Authority: ~30%
- Proof of Work: ~25%
- Opportunity / Business / AI: ~20%

Daily execution can approximate four posts/day while current evidence supports the cadence, but the percentage mix is evaluated over a rolling window rather than treated as exact daily arithmetic.

## R-005 — authority must be understandable at junior level and credible at senior level

Prefer real engineering failure modes:

- retries and duplicate side effects;
- idempotency;
- cache invalidation;
- concurrency;
- queues;
- observability;
- data contracts;
- CI/CD decisions;
- distributed systems;
- security.

Avoid textbook-style posts that only restate definitions.

## R-006 — Proof of Work demonstrates judgment

Never reduce project content to:

> “Today I added technology X.”

Prefer:

```text
problem
→ risk
→ decision
→ trade-off
→ verification
→ lesson
```

Goal: move perception from “can explain” to “can build and decide”.

## R-007 — AI/automation content must remain engineering-grounded

Avoid generic AI content such as “AI will change programming” or “10 prompts”.

Prefer:

- state management;
- retries;
- idempotency;
- audit trails;
- human approval;
- rollback;
- integration failure;
- business-process boundaries.

This enables one post to be useful to developers, recruiters and potential clients simultaneously.

## R-008 — opportunity magnets demonstrate capability without begging

Avoid making “I am looking for work” the default content pattern.

Prefer posts that implicitly communicate:

> “I can solve this class of problem.”

Examples:

- architecture for automating a SME sales process;
- first decisions before building a SaaS;
- processing 100K events/day without unnecessary microservices.

## R-009 — publish defensible technical judgment

A professional audience buys judgment, not only syntax.

Candidate opinion formats:

- microservices are not the natural evolution of every monolith;
- not every application needs Kubernetes;
- automating a bad process makes errors happen faster;
- more architecture complexity does not imply more scalability;
- more AI does not automatically produce a better product.

Claims must remain technically defensible and scoped.

## R-010 — alternate CTA types

Two useful CTA families:

1. **knowledge CTA** — low friction, binary/short-answer;
2. **experience CTA** — asks for lived experience and encourages conversation.

Goal: retain saves while increasing conversation.

## R-011 — the post is landing page #1; profile is landing page #2

Desired funnel:

```text
technical/reach post
→ curiosity about author
→ profile
→ follow
→ deeper authority/proof content
→ conversation
→ opportunity
```

Profile/Featured should quickly expose:

- role / positioning;
- backend + AI + automation + DevOps;
- real projects;
- portfolio;
- GitHub;
- 3–5 strongest proof artifacts;
- direct contact path.

## R-012 — avoid topic and angle repetition

A reused subject is not “new” merely because wording changed.

Do not repeat recent:

- topic;
- hook;
- core insight;
- diagnostic angle;
- visual structure;

unless explicitly running a continuation, controlled variation or experiment.
