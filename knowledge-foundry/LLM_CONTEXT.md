# Knowledge Foundry — LLM Context

## Role

Reason inside `knowledge-foundry/` without confusing productization with source truth.

## Read order

1. `STATUS.md`
2. `ROADMAP.md`
3. `REPOSITORY_CONTRACT.md`
4. `architecture/DOMAIN_INPUT_CONTRACT.md`
5. active `mk/*` artifacts
6. architecture model relevant to the question
7. only then descend into quarries/sources.

## Routing rules

- Technical truth belongs to the source domain.
- Educational design belongs here.
- Raw source evidence is never promoted directly into course claims.
- Compile bounded eligible knowledge slices, not whole-domain reputation.
- Prefer pointers to source-domain canon over duplication.
- A course draft is GENERATED until evidence promotes it.
- Pedagogical claims require learner/assessment evidence.
- Commercial claims require market evidence.
- Rights uncertainty blocks reproduction/adaptation when rights are material.
- Assessment scores support declared interpretations/uses, not generic mastery.
- Accessibility conformance and pedagogical inclusion are separate checks.
- Learner-identifiable raw pilot data never belongs in this public repository.
- Dependency revisions must be pinned for release candidates.

## Anti-inference rules

Do not infer:

- `popular source → correct source`;
- `domain exists → eligible course source`;
- `MK active → everything in domain is canonical`;
- `correct source → teachable curriculum`;
- `good curriculum → effective course`;
- `effective course → commercial demand`;
- `retrieval/spacing effect → universal recipe`;
- `quiz passed → mastery`;
- `completion/satisfaction → learning`;
- `WCAG pass → pedagogical quality`;
- `UDL-informed → WCAG conformant`;
- `MIT repository → every linked asset/source is MIT`;
- `public GitHub repo → open licensed`;
- `paraphrased → free of rights/provenance concerns`;
- `pilot passed once → reliable for all audiences`;
- `agent says complete → verified release`.
